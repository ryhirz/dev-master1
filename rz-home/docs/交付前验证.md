## 0. 为什么需要这道闸门

此前《上线检查清单》偏"发布运维"（Docker / 生产安全 / 浏览器走查），**缺少一道专门的"功能完整性 + 文档一致性 + 稳定性"验证闸门**。这也正是 push 前最该拦一下的环节——在代码出门前，先回答四个问题：

1. **功能是否健全完整？** 对照 PRD 功能点，逐条确认已实现、已测试。
2. **稳定性是否可靠？** 自动化测试套件是否全绿、性能是否达标。
3. **与文档是否一致？** 代码 vs PRD / UI/UX / 开发技术文档 / 既有清单，有无漂移或矛盾。
4. **有无不足与风险？** 找缺口、找 P1 延后项、找生产前置项。

> 原则（产品通）：**产品经理不是需求搬运工，是价值判断官。** 这道闸门的价值不是"跑测试"，而是"用证据做能否 push 的判断"。

## 1. 验证范围与判定标准

| 维度 | 验证内容 | PASS 门槛 | FAIL 门槛 | 当前结论 |
|---|---|---|---|---|
| 功能完整性 | PRD §4/§5 功能点 → 实现/测试追踪 | P0 100% 实现且有关键测试 | P0 功能缺失或关键路径无测试 | ✅ PASS |
| 稳定性 | pytest / Vitest / m4 联调 / 性能 | 全部通过、P95<500ms | 任一失败 | ✅ PASS（m4 需起服务后补） |
| 文档一致性 | 代码 vs 四份文档 + 既有清单 | 无矛盾、计数一致 | 出现功能性冲突 | ⚠️ WARN（发现漂移，见 §4） |
| 安全合规 | 鉴权/XSS/限频/生产前置 | 基础项落地、前置项已列明 | 高危漏洞 | ✅ PASS（生产前置项待办） |

**闸门结论判定**：任一维度 FAIL → `NO-GO`（禁止 push）；仅有 WARN → `CONDITIONAL-GO`（允许 push，须跟进）；全绿 → `GO`。

## 6. 闸门结论

```
[CONDITIONAL-GO]  FAIL=0, WARN=2（脚本侧：m4 需起服务 / 默认账号待办）
```

- **功能完整性**：✅ P0 功能 100% 实现且有关键测试，非目标无泄漏。
- **稳定性**：✅ pytest 60+2s、Vitest 11/11 全绿；性能 P95 达标（login 除外，已知）。
- **文档一致性**：⚠️ 发现 6 处漂移（D1–D6），其中 D1–D4 为计数陈旧，已在本轮修正。
- **安全合规**：✅ 鉴权/JWT/bcrypt/XSS 净化/限频均落地；生产前置项已列明待办。

**结论：CONDITIONAL-GO。** 允许 push，但须在 push 前/后跟进：① 起服务重跑 `verify_before_push.py` 消除 m4 WARN；② 确认 P1-2（web 测试或手动验收）；③ 落实生产前置项（§5 P2/上线清单 §D）。

## 7. 如何执行（可重复）

```bash
# 0) 进入后端目录
cd rz-home/backend

# 1) 一键验证闸门（pytest + Vitest + 安全速检；m4 需后端在线）
python scripts/verify_before_push.py
# 可选：仅后端 / 不起服务
python scripts/verify_before_push.py --skip-vitest
python scripts/verify_before_push.py --no-m4

# 2) 起服务后补联调回归（消除 m4 WARN）
powershell -ExecutionPolicy Bypass -File ../start.ps1   # 另开终端
python scripts/verify_before_push.py                    # 此时 m4 应 PASS

# 3) 人工比对（文档一致性，见 §4）：PRD §4/§5 功能点 ↔ 本表 ↔ 代码
```

退出码：`0` = GO / CONDITIONAL-GO；`1` = NO-GO（存在 FAIL，禁止 push）。

## 8. 接入工作流

本闸门在《上线检查清单》中的位置：**紧接编码完成、排在最前**，作为 push 的前置门禁。

> 即：编码完成 → **【交付前验证（本文档 + 脚本）】** → 上线检查清单 §B 推送与 CI → §C Docker → §D 生产安全 → §E 数据 → §F 浏览器验收。

每次 `git push origin main` 前，应先跑一次 `verify_before_push.py` 并确认无 FAIL。CI（`.github/workflows/ci.yml`）已覆盖后端单测 + 前端 typecheck/build，可作为远程二次闸门。
